## 已落地的改动

1. **更完整的模型历史**：此前 adapter 把 assistant 消息里的 shell action 丢掉，
   只把说明文字发给下一轮模型；现在恢复为原来的 JSON `content + command`，
   OpenRouter、Groq、Hugging Face 共用，测试确认不修改原始 trajectory。
2. **重复读取提示**：最近 6 步内 3 次成功读取产生相同非空输出时，提醒更换
   调查目标或读取完整实现。普通命令、失败读取和测试不会因为此检查被阻断。
3. **显式文件保护**：CLI/YAML/HTTP/评测支持受保护文件，提交前后检查内容、
   类型与权限；原始指纹随轨迹保存，恢复时继续使用，不自动覆盖外部修改。

保护文件是调用者配置的完成条件，不是文件系统沙箱；没有自动推断任务中的
全部限制，也没有让独立验收结果反馈给 agent。

## 下一步的证据依据

- 编辑应有精确匹配、匹配失败反馈、修改结果检查，避免依靠复杂 shell 转义。
- 测试数量和公开测试通过不足以代表需求正确；去重任务就是明确反例。
- 应用这些改进后，用相同配置重复运行各任务，观察稳定性；不能只保留最好一次。

## 结构化编辑工具接入后的复测

在相同模型、20 步预算和 README 保护下，跨文件 timeout 任务此次 15 步完整通过。
轨迹确认模型实际使用了结构化 `replace` 和 `create`，修改仅涉及实现与测试，
没有无关文件变化。此前相同任务因 shell 生成的语法错误耗尽 20 步。
这是单次结果，不能作为稳定成功率或严格因果实验。

去重任务首次复测 10 步提交，但返回了生成器，公开测试也仅执行了原有 1 项。
检查发现原任务文本未明确要求列表，而验收检查要求列表，这一部分是题目描述
不够明确。已修正任务文本为明确返回列表并新增可运行的 unittest；任务哈希随之
变化，因此修正前后的总体评分不直接比较。

修正后的去重任务在 20 步内实现了通过独立验收的代码，7 项公开测试全部通过，
没有无关文件变化；第 20 步运行测试后预算耗尽，没有提交，所以整体状态仍为
`max_steps`。保留原始评测结果，追加恢复步骤另存，不能记作“20 步完整通过”。
实际恢复只用了 2 步：读取 README 并提交，第 22 步进入 `completed`，提交后独立
行为检查再次通过。恢复过程中没有编辑文件；7 项测试与保护文件状态保持不变。

## 交付总结与执行回执：同配置重复 3 次

本轮要求每次提交（含被拒后重提）保留完整任务总结，另由执行器产生 `handoff`
回执。评测新增关键词式 `summary_coverage` 诊断，不改变独立代码评分。
新增元数据改变了 suite hash，不能直接把旧、新报告当成同一版本基准。

使用同一模型、20 步预算、README 保护和
`python3 -B -m unittest discover -s tests` 必过检查，连续运行 3 次，保留全部结果：

| 次数 | 模型步数 | 状态 | 独立评分 | 观察 |
| --- | ---: | --- | --- | --- |
| 1 | 8/20 | completed | 通过 | 2 项公开测试通过，回答包含 unique_by、实现文件、测试与待运行的调用者检查 |
| 2 | 10/20 | completed | 通过 | 4 项公开测试通过，回答包含功能行为、文件和测试信息 |
| 3 | 0/20 | error | 失败 | 第一个模型请求 RemoteDisconnected，未执行任务动作 |

两次完成均无无关修改，提交时检查回执为 `passed`。两份总结均命中任务核心标识，
不再只有“重新提交”，但总结措辞与剩余限制说明仍不能靠关键词证明；比如第一份
“all tasks verified”不代表所有潜在行为都已测过。三次整体通过 2 次，不将断连
失败从分母移除，也不称为真实仓库的稳定成功率；没有一次触发预算提醒。

断连暴露了现有网络重试未覆盖直接 ConnectionError 的问题。保留第三次原始
失败，随后补了对 RemoteDisconnected、ConnectionResetError、BrokenPipeError
的有限重试，以及三种 provider 的恢复与重试耗尽回归测试。验证覆盖重试上限、
退避和原始错误链；**没有再次运行该失败任务来宣称真实断连已恢复**。
重试只发生在模型请求阶段，不自动重放环境命令，也不能保证服务可用或避免
远端重复计费。
